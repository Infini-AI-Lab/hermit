OfficeQA Harness Adapters

Ten rounds of trying to make a small model answer Treasury Bulletin questions better by changing what surrounds it, not the model itself. This page records what each round changed, what it scored, what went wrong, and where the code and evidence live in this branch.

Summary

The goal. Show that evolving a harness adapter beats two alternatives. One is a plain agent harness: the Codex CLI with the model and nothing else. The other is prompt-level evolution, where only instruction text is optimized, as in GEPA or SkillOpt. The actor is GLM-5.3-flash inside Codex. The benchmark is OfficeQA Pro: 133 questions over 697 parsed U.S. Treasury Bulletin issues.

Where it stands. No evolving adapter has yet beaten its own baseline by more than run-to-run noise. The one large gain came from a hand-built, static harness in v9: environment repairs, four table tools and about 2.5 KB of advice text. It scored 31/50 against 21–23/50 for the earlier arms on the same questions. Submit-time rules on top of that lost ground (20/50). v10, now in calibration, moves evolution to where the v9 evidence points: the learner may change tool code and advice together, and every change must survive offline replay and paired re-runs before it is used.

Setup and terms

Every campaign uses the same actor, benchmark and scoring. What changes between rounds is the adapter, the learner and the operational plumbing around Codex.

Actor
accounts/fireworks/models/glm-5p3-flash inside the native Codex CLI (0.155.0-alpha.9.2 from v8 on), one fresh conversation and folder per question.
Relay / broker
A local HTTP relay between Codex and Fireworks. It records every request, retries provider defects, and in v9/v10 hosts the controller (loop guard, ledger splice, submit gate).
Sandbox
macOS Seatbelt around the whole Codex client; network reaches only the relay.
Benchmark
OfficeQA Pro (databricks/officeqa, dataset revision 763a8366): 133 questions, 697 parsed TXT bulletins plus an FTS5 search helper. Offline: no web, no PDFs.
Scoring
The official reward.py. Strict means 0% relative tolerance and is the primary metric; 1% is the same grader at 1% tolerance. Predictions are sealed before any answer is opened.
Question order
SHA-256 of seed + id. v3 used the first 70; v4–v7 and the v9/v10 pilots use the same first 50; v8 and Opus use all 133.

Terms used on this page

Harness
Everything around the model that decides what it sees and can do: the agent loop (Codex), the workspace, tools, instructions and runtime controls.
Adapter
The part of the harness we own and may evolve. In the MetaHarnessAdapter framework an adapter exports context (text), tools and agent definitions; v9 added controls.
Arm
One configuration being compared, for example "no adapter" or "cards".
W0
The starting adapter before any learning.
Learner / evolver
A model session that reads released evidence after each block and proposes adapter changes.
Block, prequential
Questions run in blocks of 5. Each question is answered before its reference is released, so learning can only help later questions.
Discordant pair
A question that exactly one of two arms got right. The sign test on these is the paired comparison.
Issue #47
An open GitHub issue on databricks/officeqa that disputes several reference answers. The 18 affected ids are scored but withheld from learners from v8 on.

How to read these numbers. The same no-adapter baseline on the same 50 questions scored 22, 17, 26, 19 and 22 in five runs (v4, v5, v6f twice, v7). GLM on Fireworks is nondeterministic at temperature 0: about 27% of questions flip between identical runs, and the standard deviation of a difference of two counts is about 3.6 questions. None of the adapted-versus-baseline gaps in v3–v8 is significant (every sign test p ≥ 0.19). v9 a vs b (12 vs 1 discordant, p ≈ 0.003) is the only paired gap that clears the noise. v8 scores are not comparable with v4–v7, because v8 fixed two measurement bugs, and v9 used different plumbing again.

Timeline v1 to v10

Each entry says what changed from the round before, what it scored and what we took from it. Code snapshots live under research/harness-adapter/officeqa/.

  1. v109-20

    70 questions, MWM vs baseline stopped

    MWM (the framework's memory-and-briefing adapter) against no adapter, with a GLM learner that wrote its own feedback. Tight budgets: 24 requests and 600 s per question.

    Result
    Not graded. Fireworks rate-limit errors, and the first learner exhausted its 48-request budget before producing anything.
    Code
    v01-v02-codex70-stopped/v1/ (protocol and stop record)
  2. v209-20

    Budgets raised, shared scheduler stopped

    Result
    Not graded. After two questions per arm we found that a Responses text.format field was misclassified as generated text, so rate refusals were not retried.
    Code
    v01-v02-codex70-stopped/v2/
  3. v309-20

    First completed run completed

    Only the transport classification was fixed.

    Result
    Baseline 23/70, MWM 24/70. Of 14 learning rounds, 6 were rejected for budget exhaustion or truncated responses.
    Lesson
    A self-supervised flash learner under tight budgets had no measurable effect, and learner infrastructure failures dominated.
    Code
    v03-codex70-mwm/
  4. v409-21

    Gold feedback, 50 questions completed

    No request or tool caps. After each sealed block the learner received the five official answers (gold-supervised online adaptation).

    Result
    22 vs 22. Only 3 of 10 learning rounds were admitted; the rest failed on budget, truncation or API errors.
    Lesson
    The answers never had a chance to act; the learner kept failing operationally.
    Code
    v04-gold-feedback-mwm/
  5. v509-22

    Full MWM, unbounded inference completed

    No wall-clock, token or cost caps. The learner could evolve every MWM layer: memory, examples, briefing, executable tools (run in a networkless container) and role specs.

    Result
    Baseline 17, full MWM 20 (7 vs 4 discordant). The adapted arm's 30 misses were 13 transport failures, 6 runaways and only 11 substantive errors.
    Lesson
    Delivery and operations, not knowledge, were the bottleneck. No learned tool was ever called in 50 episodes. From question 36 on, Codex truncated AGENTS.md at 32,768 bytes.
    Code
    v05-full-mwm-unbounded/, framework commit c0c9b87
  6. v609-24

    Checked postmortems, MWM and prompt-only completed

    Two profiles ran in parallel: full MWM, and prompt-only (a single learned ADAPTER.md served inside AGENTS.md). After each block the learner walked every failure down a ladder (S1 vintage, S2 table, S3 row/column/units, S4 cells, S5 formula, S6 format, S7 harness) with checkers verify_cell and verify_answer. Lessons were replayed every block. Attempts v6c–e were abandoned: a provider-edge 403 killed a learner round, and one question ran 98 minutes, which led to a 3,600 s wall clock.

    Result
    MWM 24 vs baseline 26. Prompt-only 25 vs baseline 19 (11 vs 5, p = 0.21). The two baselines differ by 7 on an identical setup.
    Lesson
    The replay only checked citations: an answer check compares against the reference string, so no lesson was ever demoted. AGENTS.md grew to 52 KB (MWM) and 97 KB (prompt-only).
    Code
    v06-full-mwm-and-prompt-only/, framework snapshot commit a9d0976
  7. v709-26

    Cards verified by paired re-runs completed

    The adapter became a deck of cards: one rule each, with scope, claim (≤ 600 B) and unless. The learner may only propose; each card is admitted after the actor is re-run with it on its support questions and on 2 control questions, twice each.

    Result
    Cards 26 vs baseline 22 (9 vs 5, p ≈ 0.42). 6 of 16 verified proposals admitted; AGENTS.md grew only from 1.6 KB to 5.7 KB.
    Lesson
    The verification works but is thin: one support question, two runs, and controls that flip on their own.
    Code
    v07-cards/, framework harnessadapter/architectures/cards
  8. v809-26

    All 133 questions, three arms completed

    Separate roots for none, prompt-only and cards, with five fixes found by a baseline-variance audit: provider defects are re-sent instead of graded, reasoning effort is actually forwarded, and the correct Codex binary is pinned.

    Result
    none 62, prompt 64, cards 55. Cards led through question 75, then fell behind: on questions 76–125 it scored 15 against 22 and 25.
    Lesson
    Showing the whole deck on every task turned one card ("take the latest issue printing") into a general habit. That phrase appears in 79 of 133 cards runs and in none of the others.
    Code
    v08-pro133-three-arms/
  9. ref09-28

    Opus reference and divergence analysis analysis

    Opus 5.5 solved all 133 in the same offline workspace (87 correct). Then, for every question Opus got right and a GLM arm got wrong, we located the step where GLM left the right path.

    Result
    GLM had the right evidence in its own output in 97 of 103 failures. Relevant text was in context in 32 of 33 prompt-arm failures but fully followed in 2. The smallest fix was a check, a tool or a control far more often than more text.
    Code
    opus-reference/, divergence-analysis/
  10. v909-28

    Mechanism adapter pilots done

    Environment repairs for every arm, four table tools, a ledger re-injected after context compaction, a loop guard, and a submit gate running declarative rules. A 2×2 design {text, mechanism} × {static, evolve}.

    Result
    Pilot 1 on 50 questions: text-static 31, mech-static 20, text-static at T=1.0 24. Pre-registered verdict for the mechanism: NO-GO. Pilot 2 (mechanism with the advice text restored) stood at 13/25 vs 15/25 when stopped.
    Lesson
    The gain came from tools and text up front. Checks at submit time arrive too late, and a gate makes the model verify less.
    Code
    v09-mechanism-adapter/
  11. v1009-29

    Tools become evolvable adapter content in progress

    GLM + Codex stays clean. SEED text, tool code, tool usage text and controls all belong to the adapter. The harness learner may patch tool code; a revision must pass static screens, an offline replay of recorded tool calls and paired actor re-runs.

    Status
    Built and reviewed (503 tests). The paid calibration was running at snapshot time; five first-round roots are prepared and have not started.

MWM and prompt-only (v3–v6)

MWM stores learned knowledge as memory files, a briefing, examples, executable tools and role specs, and serves them to Codex through AGENTS.md and an MCP tool. Prompt-only serves one learned document. Both learners saw the released references and wrote lessons with checks attached. The example below is a lesson the v6f MWM learner wrote and the controller marked as verified. Its answer checks carry reference strings (redacted here as «N»), which is why the replay could never fail.

Cards (v7–v8)

The cards architecture (harnessadapter/architectures/cards, evolver in harnessadapter/evolvers/cards/block.py, design in docs/design/2026-09-24-cards-evolver.md) answers two MWM problems. Every served rule is a unit that can be attributed, and nothing is served until the actor itself has been re-run with it.

1ProposeLearner calls propose_card; at most 2 per block.
2ScreenNo question ids, file names, answer numbers or 8-word copies; must fit 16,384 B.
3Re-runActor with deck + card on support questions and 2 controls, k = 2 each.
4JudgeSupport mostly right, no control wrong in every run, output tokens ≤ 3×.
5AdmitCard compiled into the deck for later questions.

Opus reference and divergence analysis

To learn what GLM does wrong, we needed a strong solver on the same material. Opus 5.5 solved each question in a clean copy of the workspace (same corpus, same search helper, no web), and a second Opus pass reviewed each answer. The predictions were sealed, then graded with the pinned reward.py: 87/133 strict and 103/133 at 1%. Opus had no time limit and a reviewer pass, so this is a ceiling reference, not a fair arm. Its solve logs contain reference-equal answers and are not in git.

Then 22 analyst agents compared, for each of the 54 questions where Opus was right and some GLM arm was wrong (103 failed runs), the GLM trajectory with the Opus solution. Each recorded the first step where GLM diverged, whether GLM had seen the right evidence, whether the adapter text was relevant and followed, and the smallest mechanism that would have fixed it.

Environment defects surfaced by the analysis. They affected every arm. zsh heredocs failed because the sandbox blocks /tmp and zsh uses TMPPREFIX, not TMPDIR; this was hit in 131 of 133 no-adapter runs. rg was denied, python3 hit the Xcode stub, the actor Python had no numpy, and Codex silently cut long tool outputs to about 10 KB. A separate replay of the v8 records found that context compaction fired near 245K tokens, and only 12 of 72 compacted runs were right.

v9 mechanism adapter

The divergence analysis said that GLM usually sees the evidence and then chooses wrongly, and that text alone rarely changes its behavior. v9 therefore moved the adapter's knowledge from instructions into machinery that runs. Its design is in v09-mechanism-adapter/design/DESIGN.md, and each layer was built and reviewed separately.

L0Environment kitFrozen Python 3.12 with numpy/pandas, rg, zsh temp-dir repair, narrowed Seatbelt read roots, multi-agent off, explicit auto-compact at 244,800 tokens. Given to every arm, including plain.
L1Pack toolsfind_tables, show_table, printings, calc over a 147 MB tables index of the corpus. Pages ≤ 8 KB; cells tagged with repairs and identity checks.
L2Broker ledgerThe relay records commands, observed values and calc results from the tool outputs it forwards, and splices a summary back in after a context compaction.
L3Loop guardThe third identical command gets a harness note. In an offline replay of v8 records, loop detection was the one checker signal that separated wrong runs from right ones (84% precision).
L4Submit gatesubmit --answer goes to the broker; declarative rules may return one finding with an offer. The model chooses Accept or Keep.
L5Scoped notes≤ 600 B each, keyword-triggered, ≤ 3 per question, 16 KB text budget.

The pre-registered design was a 2×2 factorial plus a plain arm. Text arms deliver the seed knowledge as advice in AGENTS.md; mechanism arms deliver the same knowledge as executed rules. Each arm comes in a static version and an evolving one, and learners on both sides get identical inputs. The static arms exist to separate the value of the starting adapter from the value of evolution: evolve vs static on the same side is what earns the word "evolving".

What arm b saw instead (pilot 1: submit instructions only, 829 B)v9-p1-b/runs/episodes/001/workspace/AGENTS.md
# Finishing a question

- When you have an answer, run `submit --answer "<answer>"` (add `--alt "<other>"` when you also
  considered another value). The harness checks it and prints either `recorded` or one finding.
- A finding names one possible problem with the submitted answer. When it shows `Offer: <value>`, the
  harness computed that alternative itself, from your own calculation with one input replaced.
  Accept: run the `submit --answer "<value>"` line it prints. Keep: run
  `submit --answer "<your answer>" --keep "<reason>"`. Either is fine; the choice is yours.

Both arms had the same tools and README. The only difference was where the knowledge sat, and this turned out to be the design's main flaw: the mechanism arm lost the proactive advice.

Pilot 2 (2026-09-29) gave the mechanism arm the full advice text plus the submit section. It hid --alt and disabled five rules with a pre-registered lowest-precision procedure, leaving answer_count, later_printing, period_match, recompute_final and scale. It was stopped after 25 questions and never sealed. The unofficial score was 13/25, against 15/25 for text-static on the same questions and 9/25 for pilot-1 mech-static. The rules fired on none of the questions where the two arms differed, except one where the candidate was already wrong. And with a gate present, the model ran printings less: 29 calls versus 104 on 18 questions.

What v9 taught. The errors that decide OfficeQA happen early: interpretation, table choice, vintage. A check at submit time sees only the final number and arrives too late. The large gain came from what the model saw: repaired environment, better tools, advice up front. So v10 evolves those, and keeps the loop guard, which is free.

Learner and admission

Both v10 learners are GLM-5.3-flash sessions with the same evidence tools: episodes, corpus search, verify_cell, verify_answer, calc, and reading the adapter. The harness learner adds four functions: stage_tool_patch, stage_tool_file, try_tool and propose_revision. A revision is a bundle of tool edits, USAGE text and optionally a note.

1 · $0StageExact-substring patches (≤ 20) or new files ≤ 16 KB; try_tool to test.
2 · $0ScreensPaths and caps; Python compiles, no exec/eval/process/network; diff leak screen for question text and reference-like constants.
3 · $0ReplayUp to 80 recorded invocations; no exit-code regressions or broken first lines; must change an expected command.
4 · paidPaired re-runsSupport questions ×2 plus 2–4 controls ×2; controls changed by the replay must stay right in every run.

The admission judge for a tool revisionv10-tool-evolution/plumbing/learner_common.py
def judge_revision(runs, originals, strict_controls=(), k=K) -> dict:
    """The cards judge for a tool revision (DESIGN §5): same support / control rules, the output-token
    ratio recorded but not gating, and a replay-changed control (`strict_controls`) that misses even one of
    its K runs rejects."""
    base = judge(runs, originals, k)
    strict_missed = sorted({r['q'] for r in runs if r['role'] == 'keep' and r['q'] in strict_controls
                            and not r.get('excluded') and not r['strict']})
    strict_ok = not strict_missed
    admitted = base['support_ok'] and base['keep_ok'] and strict_ok

Calibration. Before the paid round, one harness-learner session runs on the finished v9-a evidence. It answers a single question: if d later admits nothing, was that the learner or the pipeline? The first paid attempt hit the learner's 2M-token budget and had two staged patches refused by an over-strict leak screen. The budget was raised and the screen now refuses only data-like strings. In the attempt running at snapshot time, a bundle (printings_latest_value_line) passed every screen and the replay: 80 of 80 jobs ran, 9 outputs changed, 0 regressed. It was the first tool revision to reach paired re-runs.

Remaining before the paid round: finish calibration, fill the last PREREG slot, copy the hashed PREREG and calibration record into each root, run a readiness smoke per root, then start all five roots behind a shared barrier.

What we learned

  1. Operations first. Most early "results" were infrastructure: rate limits, envelope misclassification, runaways, compaction near 245K tokens, AGENTS.md truncated at 32 KB, reasoning effort silently stripped, zero-usage completions graded. Fix and audit the plumbing before judging any learner.
  2. One run cannot measure an adapter. The same baseline scored 17 to 26 on the same 50 questions. Comparisons need paired designs, repeats, and a noise band fixed in advance.
  3. GLM sees the evidence and then chooses wrongly. Right evidence was on screen in 97 of 103 failures. Relevant text was present but followed in 2 of 32 cases. Behavioral advice such as "don't loop" was ignored 13 times and helped 0 times.
  4. Broad text overreaches. A narrow card about fiscal-year outlays became "always take the latest printing" in 79 of 133 runs. A single disputed example became a standing rule about monthly rows.
  5. Tools and environment carry the gain. Repairs + four table tools + short advice lifted GLM to 31/50, from 21–23/50. This is the one effect well outside the noise, and it is still a development-set number.
  6. Late checks don't help, and advisory gates can hurt. Submit-time rules can't catch interpretation or table-choice errors, and the model verifies less when it expects a check. Offering the model's own alternative back as if it were an outside verdict flipped right answers.
  7. Verification must be able to fail. Citation replay never demoted a lesson. Paired re-runs with k = 2 and 2 controls are too thin against a 27% flip rate. Offline replay of recorded tool calls is cheap and deterministic, and it is now the first gate for code changes.
  8. Temperature 1.0 trades loops for accuracy. It ended every loop and cost 7 of 50 questions, mostly through less verification and interpretation coin-flips.

Open questions

  • Does tool evolution add anything over notes? This is the v10 d-vs-e contrast. It needs the calibration to show the pipeline can admit a revision at all.
  • Held-out confirmation. Every positive number so far is on questions that informed the design. Candidates: non-Pro OfficeQA (answers are gated on Hugging Face, so a download exposes them to whoever runs it) or SpreadsheetBench. Plan for 3 repeats per arm and a mixed-effects model.
  • Learner strength. Every learner so far has been GLM-5.3-flash. The cards design recommended a stronger learner, but it was never tried.
  • Transpilation control and advise-vs-decide. Translate each admitted mechanism into text for the text arm. Separately, compare the harness advising the model against the harness deciding a pre-registered convention, such as latest printing unless a date is pinned.
  • External data. Several questions need CPI or exchange-rate series that are not in the corpus. Supplying one table to every arm is an open decision.
  • Issue #47. 18 references are disputed. They are scored but withheld from learners; results are reported with and without them.

Prompt-optimizer baselines (GEPA, SkillOpt) are tracked as a separate task and are not part of this branch.
