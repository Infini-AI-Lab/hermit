# Evolution guide: Animation Workshop

Maintain reusable making capabilities for web-based physics animations, including liquids, cloth, rigid bodies and articulated motion. The current task supplies experience and a diagnostic case; it must not become the adapter's identity or a universal scene specification.

Three content forms are first-class: methods/ for decisions and tradeoffs, implementations/ for inspectable and adaptable source, and examples/ for small runnable integrations, variations and failure cases. Prefer cohesive capabilities with identifiable scene boundaries. Describe assumptions, units, inputs/outputs, state and customization points, plus the essential behavior an actor should check after adaptation. Do not require every item to have every artifact, force a universal physics engine, or fragment useful code into disconnected micro-tools. A complete scene is allowed, but label its scope and explain the boundary between reusable mechanics and scene integration.

index.json catalogs entries with id, kind (method/implementation/example), title, summary, scope and relative path. Optional metadata can record assumptions, related entries, adaptation guidance, essential properties, checks, transfer evidence, provenance and known gaps. These are documentation choices, not new required manifest fields. Keep referenced paths valid.

briefing.md is a concise capability map: when to use each capability, what assumptions limit it, where source/examples live, and what needs adaptation. Do not write a global "current task is this scene" instruction or default to copying the latest whole website. preferences.md records the source, task/user scope, supersession and aspects explicitly liked. Keep a brief maintenance/journal.md of changes, trials and failed reuse; no MWM docket or fact timestamp schema is required.

When continuing an existing scene-centered adapter, preserve its working examples and provenance, move latest-task prescriptions into scoped records, and extract the useful shared behavior incrementally. An old case may remain the only tested scope; do not relabel it general without evidence. The internal structure can evolve while retaining valid public exports and complete source access.

All core files are evolvable, including interfaces. Framework code, original LearningMaterial and control state are not editable. Prefer readable JavaScript for browser runtime mechanisms where suitable; Python or other construction aids are also allowed. Additional callable tools may use the normal manifest, but are optional. The delivered animation must run without MCP.

Within the available budget, check the observed failure and one structurally different diagnostic case using the relevant shared implementation. Record what changed at the scene boundary and what required core rewrites. A self-authored variation is not held-out evaluation; parameter-only variants do not establish structural reuse. If a renderer or budget is unavailable, report the missing check and limit the capability's claimed scope. Distinguish actual user feedback, AI review, measurements, source inspection and self-assessment. Identify the final code revision actually tested or rendered; stills and numeric proxies do not prove realism, smoothness or transfer gains.
